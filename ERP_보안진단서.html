ERP 보안 진단서 & 즉시 조치안

보고서 「보안」장 근거 · Executive Summary 반영용 · 기준일 2026-07-18

Executive Summary — 3줄 요약

⚠ 최우선 보안 사안.
  1. ERP는 로그인 없이 익명 키(publishable)로 클라우드에 접속하며, 이 키는 모든 화면에 포함되어 GitHub에 공개되어 있다.
  2. 클라우드(app_state) 정책이 익명 사용자에게 읽기·수정·삭제를 전부 허용 — 실증 확인됨(키만으로 데이터 삭제 성공). 즉 키를 아는 누구나 전 데이터 열람·변조·일괄 삭제 가능.
  3. 우선순위 원칙(안전·법규 > 품질···)에 따라 본 건은 품질·납기보다 앞선 즉시 조치 1순위. 핵심 방어는 (a)삭제 차단 (b)자동 백업 (c)민감정보 분리.

1. 취약점 진단

#취약점심각도내용 / 근거
V1익명 전체권한(RLS)높음app_state에 익명 SELECT·INSERT·UPDATE·DELETE 모두 허용. 실측: publishable 키만으로 테스트 키 삭제(204) 성공 → 악의적 전 데이터 삭제·위조 가능.
V2민감정보 익명 노출높음safety_reports(이상안전신고·사진)에 외국인 근로자 정보·현장 사진 포함 가능 → 익명 열람 시 개인정보·영업비밀 유출.
V3감사로그 부재중간누가·언제·무엇을 바꿨는지 기록 없음(updated_at·src만 존재). 사고 시 추적·복구 근거 부족.
V4백업 체계 부재중간일괄 삭제·손상 시 되돌릴 정기 백업 없음. (익명 삭제가 가능한 만큼 백업이 최후 방어선)
V5버전·형상관리 위험낮음파일명 버전(v1→v379)·단일 52MB 파일 → 롤백·변경추적 취약(형상관리 장과 연계).
오해 정정. "키가 공개된 것" 자체는 Supabase 설계상 정상(publishable 키는 공개용)입니다. 진짜 문제는 그 키에 붙은 권한(RLS)이 너무 넓은 것 — 조치의 초점은 키 숨기기가 아니라 권한 축소입니다.

2. 즉시 조치안 (단계별)

단계조치대상비고
즉시익명 DELETE 차단 — RLS에서 삭제 정책 제거(익명은 읽기·쓰기만). 삭제는 관리자만.V1Supabase 대시보드 정책 수정. 앱은 삭제를 거의 안 쓰므로 영향 적음.
즉시자동 백업 — app_state 전체를 매일 JSON으로 내보내 보관(3-2-1). 삭제·손상 시 복구.V4간단 백업 화면/스크립트로 구현 가능.
단기민감정보 분리 — safety_reports 등 개인정보 포함 키는 별도 테이블+접근제한, 사진은 만료링크.V2보존기간 규정 수립 병행.
단기공용 접근 게이트 — 사내 공용 비밀번호 또는 Supabase Auth로 최소한의 인증 추가.V1로그인 없는 편의성과 절충 — 사내망/공용PIN 수준.
중기감사로그 — 변경 이력 테이블(트리거)로 누가·언제·무엇 기록.V3사고 추적·IATF 심사 대응.
중기형상관리 정비 — 파일명 버전 → git 브랜치/태그, 52MB 단일파일 분할.V5보고서 「Git 구조」장과 연계.
보상 통제(현실적 최선). 로그인 없는 편의성을 당장 포기하기 어렵다면, ①삭제 차단 + ②매일 자동 백업 + ③민감정보 미저장/분리 3가지만으로도 최악(전삭제·유출)의 대부분을 막습니다. 이 3건을 이번 주 내 착수 권고.
